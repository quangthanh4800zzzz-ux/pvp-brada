# Architecture

## Layers

```
shared/                    pure types + constants, no runtime deps
  types/     common.ts, input.ts, character.ts, map.ts
  constants/ game.ts (TICK_RATE, stats, combo, guard, round constants)
  math.ts    clamp / lerp / approach

client/src/
  core/       FixedTimestepLoop (injectable rAF/clock, headless-testable), EventBus, DataLoader
  physics/    deterministic AABB world: RigidBody, PhysicsWorld
  combat/     FighterSim, BattleSim (state machine, hitboxes, damage, combos, rounds)
  animation/  manifest types + validator, FighterAnimator (Phaser-side only)
  systems/    SettingsSystem (storage-adapter), InputSystem (source-adapter, buffer)
  scenes/     Boot, MainMenu, Battle, Training, Settings (all Phaser)
  ui/         BattleHud, FxLayer (pooled), MapRenderer
  ai/ networking/ audio/  (empty — Phases 6/7/10)
  tools/      png.mjs + generate-sprites.mjs (procedural sprite pipeline)

server/                    Phase 7 scaffold, not implemented
tests/                     vitest, drives BattleSim headlessly with real JSON data
```

## Deterministic simulation

- One `BattleSim.step([intent1, intent2])` call = exactly one tick at `TICK_RATE` 60.
- `FixedTimestepLoop` accumulates real elapsed time and steps the sim in fixed slices; render runs once per frame.
- No `Math.random`, no wall-clock reads, no object ordering that depends on iteration randomness inside the sim. Physics step order is fixed: movers → zone modifiers → gravity → X-resolve → Y-resolve (one-way landing via prev-bottom check) → friction/drag → bounds clamp.
- Because the sim is Phaser-free with injectable inputs (`ManualKeySource` / intent arrays), vitest tests run the exact same combat code as the browser and (later) the server.

## Frame-locked animation

Attack animations are not time-driven. `FighterAnimator` reads `stateFrame` from the simulation and positions the sprite animation with `anims.setProgress(...)` so the visible frame and the active hitbox window can never drift apart. Locomotion animations (idle/walk/run/jump) are time-based.

## Data-driven content

- `client/public/data/characters/*.json` — stats, attacks with full frame data (startup/active/recovery, hitbox, guard height, knockback, armor, cancels), passives.
- `client/public/data/characters/*.manifest.json` — animation manifest (per-animation frame counts, fps, loop flag, frame events), generated by `npm run sprites`.
- `client/public/data/maps/*.json` — solids, one-way platforms, movers, modifier zones (gravity/friction/movement/force), spawn points, bounds.
- `DataLoader` + `validateManifest` validate data at boot; `tests` load the same files from disk (no stand-in data).
- Balance lives in JSON (`shared/constants/game.ts` holds engine-level constants only: tick rate, default gravity, combo scaling curve, guard windows, round rules).

## Sprite pipeline

`client/tools/generate-sprites.mjs` renders a skeleton-based humanoid procedurally (pose interpolation between keyframes) into 48×48 frames, packs them into per-animation horizontal strips, emits PNGs (pure-Node encoder in `png.mjs`, zlib/deflate) plus the manifest consumed by `BootScene` (`load.spritesheet`) and validated by `validateManifest`. Sprites are replaceable: drop real sheets + a matching manifest in and no engine code changes.

## Settings

`SettingsSystem` persists graphics / audio / input sections through an injectable `StorageAdapter` (localStorage in the browser, in-memory map in tests), detects key-binding conflicts, validates on load, supports export/import and per-section reset.

## Phase 7 (multiplayer) plan

The authorative server will import `shared` and re-use `BattleSim` verbatim: clients send `Intent` inputs per tick over WebSocket, the server steps the sim and broadcasts state snapshots with per-input acks for client prediction + reconciliation. `server/simulation` exists as a scaffold for this; nothing is wired yet.
